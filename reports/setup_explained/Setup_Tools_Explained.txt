YOUR SO-101 SETUP — THE TOOLS EXPLAINED
A short companion to the project report. Examples refer to our actual implementation.

1. The setup and what OpenCV does
=================================

SO-101 MJCF model — the virtual robot
MJCF is MuJoCo’s XML model format. It describes the robot’s parts, shapes, joints and how they connect. We reused an existing SO-101 model instead of reconstructing its mechanics from photographs. In your setup, this is the white virtual arm; the desk and approximate camera holder were added around it. File: assets/so101/so101.xml.

Measured joint feedback — where the real arm actually is
The motors report their encoder positions. We convert those readings into the virtual robot’s joint angles, including the elbow, wrist-bend and wrist-roll offsets we adjusted together. For example, bending the real elbow updates the simulated elbow. This is measured position, distinct from the position we ask the motor to reach. Code: command_mapping.Mapping.

Overhead and wrist cameras — two different jobs
The fixed overhead camera observes the table so the program can estimate object and plate locations. The wrist camera gives a close view near the jaws. We attempted to calibrate its optical mounting, but validation was poor; it currently helps you observe the grasp rather than supplying trusted metric localization.

Checkerboard calibration — turn pixels into useful geometry
OpenCV finds the printed checkerboard corners and estimates focal lengths, image centre and lens distortion. Your printed 100 mm bar measured 96 mm, so we used 24 mm squares instead of nominal 25 mm squares. This corrected the metric scale. Camera pose relative to the table and arm required separate registration. Functions: cv2.findChessboardCornersSB(), cv2.calibrateCamera().

Fiducial detection — recognize a known reference marker
A fiducial is a deliberately designed visual marker with identifiable corners. We temporarily attached an ArUco marker to the fixed gripper structure and observed it at different arm poses. Its detected corners helped fit the camera-to-robot relationship. This is what the printed gripper marker was for. Function: cv2.aruco.ArucoDetector.

Image differencing — notice something changed
The program compares the current table image with a saved baseline. Persistent color changes suggest an added or moved object. For example, adding the second box produces a new changed region. Color compensation and robot masking reduce false changes from lighting or arm movement. Code: scene_changes.Changes.

Contour geometry — estimate shape, width and direction
A contour is the outline of an image region. We project it onto the calibrated table plane and estimate a rectangle. For your small box, this provides an approximate width and long-axis direction for opening and orienting the jaws. Shadows or tall objects can bias this estimate. Code: scene_changes.Plane.

Destination matching — find the plate again
When you move the yellow plate, the program searches the new image using reference features, color/ellipse geometry and template matching. It updates the destination before planning rather than deliberately aiming at its old coordinates. Failed detection stops planning. Code: basket_tracking.measure_basket().

2. What MuJoCo and SciPy do
===========================

MuJoCo geometry — describe where solid parts are
MuJoCo stores the robot’s link shapes and their positions. We also use a table plane and simple object proxies. For example, before descending toward the packet, the planner checks sampled arm and holder geometry against the table. These are approximate checks, not complete protection against cables, self-collision or every tabletop obstacle.

Forward kinematics — angles in, fingertip position out
Given shoulder, elbow and wrist angles, forward kinematics calculates where the gripper ends up. For example: “With the elbow bent this much, how high are the fingertips?” MuJoCo evaluates the model; our ReachSolver.position() retrieves the gripper reference position using mujoco.mj_forward().

Rendering — draw the predicted pose
Rendering turns the three-dimensional model into an image. This produces the virtual arm view and the overlay beside your overhead image. It lets you inspect whether the simulated holder or gripper is aligned and preview a proposed reach. A convincing rendered motion does not prove that the physical arm completed it.

Separate contact experiments — test virtual touching and lifting
In contact_preview.py, a simulated highlighter is a free object that can interact with the fingers and table. We tested closing, lifting and releasing it using MuJoCo contact physics. These experiments used assumed mass and friction. They differ from the ordinary real-arm planner, which assumes the carried object stays in the grasp.

SciPy bounded nonlinear optimization — find usable joint angles
Inverse kinematics asks the reverse question: “Which joint angles put the jaws over this box?” scipy.optimize.least_squares() repeatedly adjusts candidate angles to reduce position and orientation errors. “Bounded” means the search respects joint-angle limits. “Nonlinear” means fingertip position changes through coupled rotations, rather than a simple straight-line formula.

Optimization example from your setup
When you moved the object, ReachSolver.solve_natural_grasp() searched for a new reachable grasp pose. Trying alternative wrist-roll orientations helped when one direction had already rolled too far. The solver computes angles from geometry; it does not learn them from previous grasps. It may still fail if the requested pose cannot satisfy the constraints.

Scalar root finding — choose one gripper angle for a gap
Here “scalar” means one unknown: the gripper hinge angle. scipy.optimize.brentq() searches for an angle where calculated jaw gap minus requested gap equals zero. For example, a 50 mm opening request becomes a model hinge angle. The restored second-box rule asks for estimated width minus 4 mm: a 43 mm box gives 39 mm. This commands position, not a measured grip force.

3. LeRobot, AI and one complete example
=======================================

LeRobot motor interface — communicate with the real arm
LeRobot provides the SO101Follower interface and motor-bus access. Our robot_setup.make_robot() creates it, and control_worker.Controller handles the physical command loop. For example, the planner produces a sequence of joint targets; the worker uses the motor interface to send them and read the resulting positions. The viewer itself is not a separate competing motor controller.

Calibration conventions — agree on what a motor reading means
LeRobot calibration records reference offsets and travel ranges so raw encoder values can be interpreted consistently. This was the step where you placed the arm near midrange and swept the joints by hand. Our project then added a separate motor-to-MuJoCo mapping. Motor calibration and the later visual elbow/wrist adjustments are related, but are not the same operation.

Classical geometry plus optional GPT recognition
Object outlines, tracking and plate localization use explicit image-change, color and geometry methods. The new GPT mode adds a pretrained vision-language model to identify a requested object among those outlines. Pages 4–7 explain how recognition connects to adaptive tracking and physical grasp planning.

No reinforcement-learning policy
A reinforcement-learning policy would learn actions from rewards during trials or simulation. Our arm instead follows explicitly constructed reach, descend, close, transfer and open stages, using inverse kinematics and timed joint paths. The successful grasp experiments did not automatically train a policy.

GPT selects identity; geometry and feedback control motion
The optional runtime now sends an overhead image and your object description to GPT. It returns a candidate object ID. OpenCV supplies its current footprint, SciPy and MuJoCo calculate the motion, and LeRobot communicates with the motors. GPT does not directly command the arm. This is separate from the AI assistant used to develop the software.

Example: put the small box in the plate
1. OpenCV finds the box footprint and the plate in a fresh overhead frame.
2. The calibrated geometry expresses their approximate positions relative to the robot.
3. SciPy searches for joint angles; MuJoCo calculates and displays the resulting poses.
4. A root solve converts the requested jaw gap into a gripper angle.
5. Our controller generates timed commands, and the LeRobot interface sends them to the motors.
6. Encoder feedback reports how the arm actually moved; the wrist view helps you inspect the grasp.

Scope of this explanation
This describes the inspected project implementation, including the restored second-object grip setting. Object heights remain supplied assumptions, wrist optical registration remains unaccepted, and physical grasp success is not guaranteed by a successful simulation preview. Source files and detailed evidence are indexed in the main project report.

4. Adaptive tracking: a moving target
=====================================

Why add this?
A plan made from one photograph aims at that old location even if you move the object. The live controller instead re-observes the selected object and updates the desired hover pose during the reach. This is camera-feedback control with numerical IK, not a trained motion policy. The active camera is the fixed overhead camera; wrist-guided steering was deferred because of its narrow view and unvalidated optical registration.

Step 1: acquire and find candidates — OpenCV
adaptive_grip.py reads the latest camera frame in a background Python threading.Thread with a queue of size one. cv2.remap() corrects lens distortion. scene_changes.Changes compares blurred LAB colors with the saved table baseline, compensates the median color shift, thresholds changes and applies morphological opening/closing. Contours give candidate objects. A projected robot mask suppresses the arm. This is background-change detection, not neural segmentation or dense optical flow.

Step 2: locate and associate the same object
scene_changes.Plane.footprint() projects contour points onto the calibrated tabletop and fits footprint geometry: center, width and long-axis direction in robot coordinates. adaptive_reach.observe_regions() computes an HSV histogram using cv2.calcHist(). TargetWatch.update() compares histogram appearance with cv2.compareHist(..., HISTCMP_BHATTACHARYYA), footprint size and distance from the previous observation. Several plausible matches are treated as ambiguous. This maintains identity approximately; similar objects or large jumps may require reselection.

Step 3: update IK while the object moves
live_grip.WarmGraspIK.solve() starts from the previous joint solution and uses scipy.optimize.least_squares() to reduce position and jaw-orientation error. Each live search stays near the current branch (up to 12 degrees per arm joint around the previous solution). MuJoCo mj_forward() evaluates each candidate pose. The hover target is retargeted from the saved successful reach reference, object displacement, assumed height and existing lateral correction. Warm starting saves search work; this is not a persistent learned IK memory.

Step 4: command smoothly and measure the result
Updates are attempted no faster than every 75 ms, typically around 10 Hz; the separate control_worker runs nominally at 30 Hz. JointServo limits speed and acceleration (20 degrees/s and 60 degrees/s²), clips to current joint bounds and rejects stale updates. ServoClearance checks each incremental command against the table. LeRobot sends motor goals and reads encoders. These are target rates, not measured hard real-time guarantees. Python queue/threading, NumPy, OpenCV, SciPy, MuJoCo and LeRobot provide the active implementation.

5. GPT: turn “matchbox” into a target
=====================================

Where the neural network enters
GPT is now a pretrained vision-language model in the optional operational recognition path. It identifies the requested object from an image and text. It does not output motor angles, robot coordinates, object height or gripping force. There is still no reinforcement-learning policy or model trained on our robot trials. The earlier statement that the whole runtime contains no neural network applies only to the original classical mode.

1. Build a numbered scene
After OpenCV detects contours, gpt_targets.request_payload() draws a yellow outline and numeric ID around each candidate. It JPEG-encodes the overhead frame with cv2.imencode(), then base64-encodes it. The user enters “matchbox” or “reach for the pink highlighter.” The model can only select among these candidates: it cannot recover an object the contour detector missed or separate objects already merged into one contour.

2. Send one recognition request
gpt_targets.recognize() uses Python urllib.request to POST to https://api.openai.com/v1/responses. The default model is gpt-4.1-mini, overridable with OPENAI_VISION_MODEL. OPENAI_API_KEY comes from the environment. The input contains the description and image (input_image, detail high). A strict JSON schema requests status, candidate_id and a description. store=false is set; the image still leaves the machine for the API. No OpenAI Python SDK is required.

3. Validate and reconnect to live geometry
parse_selection() accepts only a completed, non-refused response with a valid candidate ID. Missing/ambiguous results and API failures produce no new plan. The camera loop continues tracking all request-time candidates while the network call runs in a background thread. When the reply arrives, the selected candidate must still be fresh and stable, and the request must still belong to the current operation. The planner uses its updated local footprint, not coordinates invented by GPT. Enter prepares the selection/plan; G explicitly executes it.

Concrete example and evidence
The saved scene contained a highlighter, matchbox and biscuit packet. A real API test of the request “matchbox” selected expected candidate 2 in 3.52 seconds. No motor commands were sent in that test. Evidence: captures/gpt_selection_test/result.json. This is one recognition example, not an accuracy benchmark. Later live requests can number contours differently. GPT is called per request; it is not repeatedly called in the servo loop. Misidentification remains possible, so the highlighted contour is shown before G.

6. Planning a grip: from selection to hover
===========================================

The complete pipeline
Typed object description → overhead frame and OpenCV contours → GPT candidate ID → current tracked footprint in robot coordinates → grasp-pose IK and path checks → open/prepare → adaptive reach → commit target → descend → close → hold. Encoder feedback runs throughout. Hidden-object handling is described on the next page. No basket, lift or return is included in this GPT grip mode.

1. Convert measurements into a grasp request
adaptive_grip.py selects the current footprint and copies config/grasp_target.json. In GPT grip mode, opening gap is estimated width + 8 mm; closing gap is width − 4 mm, with a 5 mm minimum. Example: a 41 mm matchbox requests about 49 mm opening and 37 mm closing. Current assumptions remain 40 mm object height, 25 mm descent and the earlier 20 mm camera-left correction. GPT does not estimate these values. Different heights or soft objects may need different settings.

2. Establish an executable starting pose
mirror_grasp_plan.build_sequence() starts from the controller’s actual command. If needed, it searches for a wrist-clearance move away from the table. It then plans opening the jaws and moving inward from permitted resting margins. scipy.optimize.brentq() solves for the gripper hinge angle that produces a requested fingertip gap using simulated_reach.fingertip_gap(). Startup paths are sampled against table geometry.

3. Find the hover pose and choose a branch
ReachSolver.solve_natural_grasp() tries both equivalent object-axis directions and both wrist-roll directions, using multiple initial seeds. SciPy bounded least squares minimizes gripper-position, jaw-axis and tilt errors; MuJoCo computes the resulting positions and orientations. Accepted poses currently require position error at most 2 mm, jaw-axis error at most 15 degrees and tilt at most 30 degrees. Candidates favor smaller wrist motion. Being position-reachable does not guarantee an oriented grasp is feasible; position-only mode remains available for reaching without gripping.

4. Check the path and future descent before moving
For each candidate, build_sequence() samples the approach at 161 points and checks moving geometry and gripper/holder clearance against the tabletop. GPT grip mode also preflights grasp_tail.build_tail() for descent and closure; a candidate with an infeasible tail is skipped. G runs the preparation and then local adaptive following. At the hover, measured FK must be within 4 mm and arm joints within 3 degrees of the target; stable alignment is sustained before committing. This does not check every obstacle, cable or self-collision.

7. Descend, close, hold — including occlusion
=============================================

5. Freeze the final target and replan the tail
The program pauses streaming and waits for the motor worker to acknowledge holding the command. It then recalculates build_tail() from that actual command, rather than trusting only the earlier preflight. A changed command or incompatible target invalidates the result. Normally the target must have been stable for at least 0.6 s, followed by approximately 0.8 s of aligned tracking before committing.

6. Descend along the table normal
build_tail() requests a 25 mm downward step with the jaws open. ReachSolver.solve() finds nearby arm angles; if the result twists the tool too much, an orientation-weighted scipy.optimize.least_squares() refinement is tried. Current checks constrain descent joint excursion to 20 degrees, orientation change to 10 degrees and sampled sideways drift to 4 mm. Table clearance is checked again. Quintic interpolation smooths the joint path; the existing descent playback multiplier is 2. Encoder settling is checked before progressing.

7. Close and hold
brentq() converts the requested closing gap to a gripper angle, keeping the arm joints at the descended pose. Closure uses the existing 4× playback multiplier, checks the path and retains the requested gripper goal while holding. The controller reports sequence completion after its endpoint-settling checks. This is not force-controlled gripping and does not prove that the object is securely held; object slip or a missed grasp still requires observation. No automatic lift, plate transfer or sitting return follows.

Why a hidden target no longer necessarily stops the grip
The arm can hide an otherwise stationary object before reaching hover. FinalApproachMemory remembers the last stable target for up to 12 s and permits the final 6 cm of approach to finish at that location. Measured arm arrival is still required. Once committed, committed_grip_valid() allows disappearance during descent planning and closure: planning has a 15 s deadline; execution is bounded by the planned playback and settling allowances. Visible displacement or ambiguous matching still prevents progression. Camera-stream failure is different from an object hidden in a valid image and still triggers stopping. Movement while fully hidden cannot be detected.

What has and has not been validated
The latest combined software run passed 48 tests, including hidden-before-hover, stale/invalid recognition, target motion, ambiguity and controller checks. verify_gpt_grip.py replayed the saved matchbox through 600 ideal-feedback streaming updates and the lower/close stages; model hover error was 0.58 mm and closing gap 37.1 mm. These are software/model results, not measured physical accuracy or a grasp-success rate. Sources: adaptive_grip.py, adaptive_reach.py, live_grip.py, gpt_targets.py, mirror_grasp_plan.py, grasp_tail.py and control_worker.py. API references: developers.openai.com/api/docs/guides/images-vision and /guides/structured-outputs.

8. Closing the reality gap: recommended priorities
==================================================

The recommendation: keep measuring, then verify the outcome
A more accurate simulation helps, but it cannot predict every object movement, hidden contact or slip. For this setup, I recommend a layered loop: observe → estimate uncertainty → make a short motion → observe again → confirm contact and grasp → recover if needed. Use MuJoCo to predict feasible motion, then let measurements correct it. This section is a proposed roadmap, not a description of additional features already enabled.

Priority 1 — confirm that a grasp actually happened
Our current DONE state means the commanded sequence completed; it is not proof of possession. Add a VERIFY_GRASP state using measured jaw opening and changes in motor load/current, compared against an empty-close baseline. These motor signals are indirect and posture/friction dependent: first establish their repeatability; do not treat raw current as calibrated fingertip force. Where visibility and clearance allow, a small test lift could check whether the object moves with the jaws. Require agreement between observations before declaring success.

Priority 2 — recover from a miss instead of repeating it
Add explicit outcomes: object not found, target moved, no contact, uncertain grasp and suspected slip. For a miss, stop closing, reopen, retreat along a checked path and reacquire the object before one or two bounded retries. For a suspected slip while carrying, avoid simply opening above the table; first choose a controlled placement or stop for assistance. A retry must use a new observation and changed approach, not repeat the stale command. Keep retry count and diagnosis in the log.

Priority 3 — improve the final few centimetres
After replacing the narrow wrist camera, use overhead vision for global reaching and wrist vision for local centering and jaw orientation. OpenCV can track suitable object features and fingertip landmarks; NumPy/SciPy can estimate a local mapping from image errors to small arm corrections. Validate that mapping with held-out motions before steering. Define the image reference at the intended grasp height: the apparent midpoint between tips is not automatically the correct target at every depth. Visual servoing provides the established feedback framework [R1].

What we can improve immediately
Start with synchronized logs, an explicit uncertain/verified grasp outcome, and bounded recovery. Evaluate load/current signals without changing the active controller first. Measure object height or store a checked height per known object rather than assigning every object 40 mm. Keep GPT for semantic selection, local vision for continuous tracking and the motor worker for fast feedback. A larger language model alone will not resolve geometric bias, camera latency or hidden contact.

9. Noise, moving targets and occlusion
======================================

Estimate motion and uncertainty, not just the latest center
Extend TargetWatch with a constant-velocity Kalman filter using NumPy, or an equivalent tested estimator. Track tabletop position, velocity and uncertainty; reject implausible observations rather than chasing every contour jitter. Handle rectangular-object orientation modulo 180 degrees so a sign change does not command a wrist flip. Measure observation noise from a stationary object and tune process noise using deliberate movements. More smoothing can add lag, so evaluate both jitter and delay.

Make timestamps and latency part of the geometry
Log frame acquisition, processing completion, IK completion, command transmission and encoder sampling on a common monotonic clock. The current timestamp after VideoCapture.read() is not a guaranteed exposure timestamp. Where the driver permits, use capture timestamps and associate each image with the arm pose at capture time. Example: an object moving 20 mm/s travels 4 mm during 200 ms of delay. Predict only over short, measured latency; stop extrapolating after prolonged occlusion or abrupt motion.

Replace a fixed blind interval with an error budget
The implemented final-approach memory permits up to 12 s and 6 cm of remaining reach. It improves continuity, not observability: a hidden object can still move. A stronger policy would let predicted uncertainty grow while the target is hidden and compare it with grasp tolerance. For a 41 mm object and 49 mm opening, nominal centering room is only about 4 mm per side before accounting for angle error. If projected uncertainty consumes that allowance, reacquire the target instead of assuming its old location is correct. This uncertainty-based rule is proposed, not currently implemented.

See around the occlusion, or change the approach
When possible, fuse overhead and replacement-wrist observations of the same object with time alignment and independently validated camera geometry. If both views lose it, pause or retreat to a checked observation pose. Include visibility in candidate selection: two IK solutions may reach the same object but one lets the camera see the gap longer. Multiple cameras are useful only when correspondence and calibration are trustworthy; the rejected wrist transform must not be reused as if validated.

Use short local plans and modest compliance near contact
The existing warm IK already updates a target during approach. Extend that idea through small, checked descent increments, updating the local grasp geometry when observations remain reliable. Keep an explicit commit/contact phase so a shifted contour is not chased through the object. Soft replaceable fingertip pads may tolerate small errors; their thickness changes the effective gap and must be recalibrated. Tactile or force sensors can add contact/slip evidence [R2]. True force/impedance control requires suitable sensing and a validated actuator interface; it is not enabled merely by changing a position-control parameter.

10. Improve the model — and measure robustness
==============================================

Identify systematic error separately from random variation
Record tool-position error at several table locations, approach directions, speeds and payloads. Fit camera/base registration and joint-offset corrections with scipy.optimize.least_squares(), then evaluate on held-out poses. Replace the current single lateral correction only if a new spatial correction performs better away from its fitting points. Joint encoders cannot reveal every link deflection or gear-backlash error, so external tool observations are needed. Separate calibration drift from object-detection bias and timing delay.

Match simulation to measured behavior, where useful
If speed, overshoot or contact behavior becomes the bottleneck, identify actuator delay, damping, friction and compliance from recorded motion/contact data. MuJoCo provides a system-identification toolbox intended to fit model parameters to sensor recordings [R3]; assess compatibility before adopting it. Fit only parameters the measurements can constrain and test on a different trajectory. Detailed contact simulation still depends on uncertain object friction and deformation, so it should not replace physical grasp verification.

Stress-test variations instead of one ideal scene
Build a reproducible trial set with object translations and rotations, different heights, lighting changes, brief occlusion, deliberate target movement, added latency and distractor objects. Replay recorded images for perception tests; vary plausible camera/joint offsets, object geometry and contact parameters in MuJoCo for motion tests. This is uncertainty testing, not training by itself. Domain randomization becomes a learning method only if those varied simulations are used to train a policy. Real trials remain necessary to measure transfer.

Measure task outcomes, not just planner success
Report first-attempt grasp success, success after recovery, false success declarations, dropped objects, failed selections, cycle time and the tail of the position-error distribution. Separate a planned pose, executed motion and verified object possession. As an initial comparison, repeat a fixed set of poses for each of the three objects under the old and new methods; retain every failure, not just good demonstrations. Increase the trial count before claiming reliability, report counts and uncertainty, and compare methods under matched conditions.

Suggested implementation order and learning later
1. Instrument timing and measure per-object height.
2. Add grasp verification and bounded recovery.
3. Add uncertainty-aware target estimation and visibility-aware approach selection.
4. Replace/calibrate the wrist camera and enable local visual correction.
5. Fit systematic residuals; add tactile sensing if contact remains unreliable.
Only then consider a learned segmentation model for touching objects, or a small learned residual/grasp-quality model from labelled trials. Keep held-out tests and geometric limits. A persistent IK solution cache can accelerate search, but does not correct reality mismatch by itself.
